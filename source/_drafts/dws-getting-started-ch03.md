> ⚠️ 这是草稿。建机器人的那条链路依赖上游服务端工具上线,本文里凡是涉及「建号」的命令都标了「目标态」,等真机跑通、关键演示录好我再转正式发布。先把架构和取舍这层想清楚 —— 这才是这篇真正想讲的。

前两篇,Ch.1 你坐在终端里一条条敲 dws 命令,Ch.2 你把活用大白话甩给 Claude / Cursor 让它去拼命令。两篇的共同点是 —— **你在指挥**。

这篇换个姿势:把机器人挂到钉钉群里,**员工问、它自己答**。也就是大家都想要的那个「企业答疑机器人」。

听起来是个大工程,其实我踩下来发现,真正难的不是把机器人建出来,是想清楚一件事 ——

## 建号 ≠ 会答

很多人一上来就纠结「怎么把机器人建出来」。这步当然要做(对应仓库里那个 [PR #407](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/pull/407),`dws connect bot create` 一条命令建号 + 起 Stream 收发消息)。

但你把机器人建出来,它只是**会收消息、会回消息**而已 —— 至于回什么,它一无所知。

> **建号解决的是「机器人怎么收发消息」,不解决「答案从哪来」。**

这篇就专门解决后半句。先上一张我自己理下来的架构图,后面逐层拆:

![企业答疑机器人 · 四层架构](/img/dws-ch03/arch.svg)

接入层(建号 + Stream)PR #407 已经做完,不用操心。编排层是你的 agent 逻辑。这篇的重点是**检索层** —— 答案到底从哪几个地方来。

你大概会想到三个选项:钉钉里的文档/群/知识库/听记、本地的代码文件、或者干脆上一套专业 RAG。我的结论是:**这三个不是三选一,是分层叠加,而且顺序很重要。**

## 第一刀:别一上来就上 RAG

我见过最常见的弯路,就是一听「企业知识问答」立刻去搭向量库、灌文档、写检索服务。先打住。

钉钉自己就有一层东西叫 **AI 搜问**(`dws aisearch`),它本质上就是一套**带权限隔离的企业语义检索**。员工问「报销流程是什么」,你压根不用自己做 embedding,一条命令丢过去:

![Layer 1:dws aisearch enterprise 真跑 + 脱敏视图](/img/dws-ch03/demo01-aisearch-retrieval.gif)

> 上面这条是**真命令真跑**的,命中 20 条,跨了 im / 日历 / 待办多个来源。GIF 里标题统一打了「已脱敏」—— 因为这是公开博客,返回的是我们真实的企业内部内容,不能裸贴。你自己跑的时候看到的是真实标题。

这条命令的价值在于:

- **开箱即用**,不用你搭任何检索基建;
- **跨来源**,消息、文档、日历、待办一把捞;
- 最关键的 —— **天然带权限隔离**。它走的是调用者的登录态,返回内容受「这个人能看到什么」约束。

大量「公司 XX 政策是啥」「谁负责 YY」这类问题,到这一层就答完了。

## 第二层:命中了,再把全文捞出来

`aisearch` 给你的是线索和片段。命中某个明确的文档/会议之后,用 dws 把全文捞出来喂给模型:

| 资产 | 命中后怎么取全文 |
|---|---|
| 钉钉文档 | `dws doc search` → `dws doc read` / `dws doc block list` |
| 知识库 Wiki | `dws wiki space search` → `dws wiki node` → `dws wiki doc` |
| 听记纪要 | `dws minutes list` → `dws minutes get summary` / `transcription` / `todos` |
| 群聊 IM | `dws chat`(翻历史消息、取上下文) |
| 云盘附件 | `dws drive search` → `dws drive download` |

> 顺嘴提一句:钉钉这个叫**听记**,不是妙记(那是飞书的)。

Layer 1 负责「找到」,Layer 2 负责「读全」。这两层叠起来,已经能覆盖绝大多数企业答疑场景了。

## 第三层:什么时候才真的需要 RAG

到这儿你可能问:那专业 RAG 到底还要不要?要,但**先过这个清单,满足两条以上再上**:

- [ ] 语料上万篇,且 `aisearch` 召回质量确实不够;
- [ ] 需要 chunk 级的引用溯源、相关性打分、自定义重排;
- [ ] 多模态 / 复杂文档结构,原生检索 hold 不住;
- [ ] 数据有私有部署要求,不能进钉钉。

如果真要上,推荐的姿势是:**离线**用 dws 把钉钉资产(文档/知识库/听记)增量同步进向量库,**在线**走向量检索 + 重排。但有个坑必须提前说 ——

## 权限,是这篇里最该划重点的

这是企业答疑机器人和玩具 demo 的分水岭。

dws 的 `aisearch` 和各资产命令,走的都是调用者登录态,**权限隔离是钉钉白送给你的**。一旦你自己上外接 RAG,把全公司文档一股脑灌进一个不分权限的 index —— 机器人就会把 A 部门的薪资文档,答给 B 部门来问的人。

> 这不是 bug,这是泄密事故。

所以记住几条红线:

- 机器人答任何问题,都要**以「提问人身份」约束可见范围**,不能越权;
- 外接 RAG 最大的隐性成本**不是搭向量库,是重新自己复刻这套权限过滤** —— 这件事钉钉原生免费给你,自己做要命;
- 别图省事让机器人挂个超级管理员凭证答所有人,那等于把所有权限闸门一次性关掉;
- 答疑留痕建议接上审计日志(仓库里有这块能力),合规可追溯。

## 那「本地代码文件」这条路呢

也有用,但用在刀刃上:适合那些**还没沉淀进钉钉**的东西 —— 工程代码、内部 SOP、零散的 markdown。

做法上别上重型 RAG,`ripgrep` 全文检索 + 必要时一个本地小索引就够了。但要认清它的两个毛病:**没人维护就会烂**(本地文件不像钉钉文档有人持续更新),所以回答里务必标「知识截止时间 / 来源文件」。更好的归宿其实是 —— 把这些内容沉淀进钉钉知识库,之后统一走 Layer 1,省掉单独维护。

## 把它跑起来:建号那一步(目标态)

知识来源理清楚了,回到「怎么把机器人建出来」。对应 [PR #407](https://github.com/DingTalk-Real-AI/dingtalk-workspace-cli/pull/407),思路是一条命令建号、再起 Stream 收发:

```bash
# ⚠️ 目标态:依赖上游服务端 MCP 工具上线,当前开源版二进制尚未包含
dws connect bot create        # 异步建号:内部 submit 拿 taskId → 轮询到 SUCCESS
                              # 拿到 robotCode / clientId / clientSecret
# 拿凭证起 DWClient Stream,订阅 TOPIC_ROBOT,收到消息 → 走上面三层检索 → 回
```

## 落地路线:别想着一步到位

我自己的节奏是这样:

| 阶段 | 做什么 | 验收 |
|---|---|---|
| 第 1 周 | 建号 + Stream 建联 + 直连 `aisearch enterprise` | 群里 @机器人能答出基于企业知识的问题,闭环通 |
| 第 2 周 | 加 Layer 2 精取(doc/wiki/minutes)+ 回答带引用来源 | 答案能点开溯源到具体文档/会议 |
| 第 3 周 | 攒一个评测集(常见问 50 条)+ 答不出时的兜底话术 | 召回/准确有基线数据 |
| 按需 | 对照清单评估要不要上 Layer 3 RAG | 有数据支撑,不是拍脑袋 |

## 几个我踩过 / 见过的坑(反模式)

- ❌ 一上来就上向量库 —— 大概率 `aisearch` + 精取就够了,白烧工程量;
- ❌ 把全公司文档灌进一个不分权限的 index —— 越权泄密,红线;
- ❌ 机器人挂超管凭证答所有人 —— 等于没有权限;
- ❌ 本地/向量库内容不标知识截止时间 —— 答过期信息还一脸自信;
- ❌ 跳过评测集直接上线 —— 出错了没基线,分不清是检索问题还是生成问题。
